# 要件定義 v1.0

> 初回ヒアリング（2026-10-30）の回答をもとに作成し、同日に主要な項目を確定。
> リポジトリ作成後はルートに置き、変更は PR で行う（要件が変わった履歴を残すため）。

## 1. 概要

| 項目 | 内容 |
|---|---|
| テーマ | 大阪府の中古マンション取引価格の予測と、価格を左右する要因の分析（茨木市を重点的に見る） |
| メインの問い | 取引価格（㎡単価）は予測できるか？予測に効いているのはどの要素か？ |
| 想定読者 | 自分（学習記録）＋ 不動産・データに詳しくない第三者（デモと説明資料） |
| 期間 | 2026-11 〜 約4週間（週8時間、合計 約32時間） |
| リポジトリ公開範囲 | Public（公開時のコスト・安全面の方針は「10. 公開時の方針」を参照） |

## 2. 背景・目的

- 実務の分析経験を、**機械学習を使った予測と要因分析** に広げたい
- 無料の公開データ（不動産情報ライブラリ・人流データなど）で何ができるかを試したい
- GitHub を使った再現可能な分析プロジェクトの進め方を身につけたい

### 学習目標（ML）
- [ ] 回帰問題の設定ができる（目的変数・特徴量・評価指標・データ分割）
- [ ] ベースライン → 線形回帰 → 勾配ブースティング（LightGBM）の順に改善を比べられる
- [ ] 特徴量の重要度（Permutation Importance・SHAP）を使って「なぜその予測になったか」を説明できる
- [ ] データリーク・過学習とは何か、どう防ぐかを説明できる

## 3. 問いと仮説

| ID | 問い | 仮説（初期） | 検証方法 | 週 |
|---|---|---|---|---|
| Q1 | ㎡単価はどの程度の精度で予測できるか | 立地・築年数・面積で大まかな傾向は予測できる（R² 0.6 以上が目安） | 時系列分割で MAE / RMSE / R² | W3 |
| Q2 | 予測に最も効くのはどの要素か | 駅からの距離 > 築年数 > 用途地域 の順に効く | SHAP・Permutation Importance | W3 |
| Q3 | 人流データを加えると予測は良くなるか | 人が多い地域ほど単価が高く、立地の情報を補ってくれる | 人流データあり / なしの比較実験 | W3 |
| Q4 | 地域・物件の種類によって効く要素は違うか | マンションは築年数、土地は駅距離がより効く | 種類別にモデルを作るか、SHAP をグループ別に集計 | W3〜4（任意） |

## 4. データ

| データ | 出典 | 粒度 | 使い道 | 備考 |
|---|---|---|---|---|
| 不動産取引価格情報 | 国交省 不動産情報ライブラリ（API / CSV） | 取引1件ごと（市区町村・地区、最寄駅、駅距離など） | **目的変数＋主な特徴量** | API は利用申請が必要 → **Day 1 に申請** |
| 地価公示・地価調査 | 不動産情報ライブラリ / 国土数値情報 | 地点ごと（緯度経度あり） | 地域の価格水準を表す特徴量 | 任意 |
| 人流オープンデータ | 国交省（G空間情報センターで配布） | 1kmメッシュ / 市区町村、月ごと | 地域の賑わいを表す特徴量（Q3） | 対象期間が限られるため要確認。取引データとの粒度の違いに注意 |
| 人口・世帯 | e-Stat | 市区町村 | 補助的な特徴量 | 任意 |

詳細は [data_sources.md](data_sources.md)。

- 対象地域: **大阪府全体で学習し、茨木市を重点的に見る**
  - 茨木市だけだと件数が少なく（年に数百件程度の見込み）、市区町村単位の特徴量（人流・人口など）がすべて同じ値になってしまい、Q3 が検証できない
  - そのため、モデルは大阪府全体で学習し、デモの初期表示・事例紹介・誤差の確認では茨木市を使う
  - 余力があれば「茨木市だけで学習したモデル」と精度を比べる実験（件数が少ないと何が起きるかの学習になる）
- 対象の物件種類: **中古マンション等**
- 対象期間: **データに合わせて変える**。取得スクリプトの引数（開始年・終了年）にしておく
  - まずは直近5年で取得 → EDA で件数・欠損を見る → 人流データと重なる期間を確認して決める
  - 期間を変えて結果がどう変わるかも実験の1つにできる
- データの置き場所: `data/raw/`（Git 管理外）。取得スクリプトだけをコミットする

## 5. 成果物（Deliverables）

- [ ] **インタラクティブなデモ**: 条件（地域・駅距離・築年数など）を操作すると予測価格と SHAP による要因内訳が変わる画面
- [ ] **コード一式**: 取得 → 前処理 → 学習 → 評価 を再実行できるパイプライン（`src/` ＋ テスト）
- [ ] **説明資料**: 問い・データ・手法・結果・限界をまとめた資料（`reports/` の Markdown ＋ デモ内で解説）
- [ ] 実験記録（Issue ＋ `experiments/results.csv`）
- [ ] CI（ruff ＋ pytest）※最小限で OK

### デモの技術（marimo に決定。W1 で触ってみて合わなければ Streamlit に変更）
| 候補 | 良い点 | 注意点 |
|---|---|---|
| **marimo** | ファイルが .py なので Git の差分が読みやすい。Polars・Altair と相性が良い。HTML に書き出して GitHub Pages で公開できる | ブラウザだけで動かす（WASM）場合は LightGBM が使えない → 予測結果を事前に計算して埋め込むか、sklearn のモデルを使う |
| Streamlit | 情報が多い。Community Cloud で無料公開できる | 中身はスクリプトなので、探索用のノートブックとは別に管理する必要がある |

## 9. リスク・懸念

| リスク | 対策 |
|---|---|
| API キーの発行に時間がかかる | Day 1 に申請。発行されるまではサイトから CSV をダウンロードして進める |
| 人流データの期間・粒度が取引データと合わない | 市区町村×年 に集計して結合する。合わなければ Q3 は「やってみた結果」として報告 |

## 10. 公開時の方針（コスト・安全面）

リポジトリとデモを公開すると、検索エンジンや AI のクローラー（Bot）を含め誰でもアクセスできる。
**「誰がどれだけアクセスしても課金が発生しない構成」** にすることを原則とする。

### 採用する構成
| 公開するもの | 置き場所 | アクセスが増えたときの課金 |
|---|---|---|
| コード・レポート | GitHub（Public リポジトリ） | なし |
| デモ | GitHub Pages（marimo を静的 HTML に書き出し、ブラウザ内で動かす） | なし（サーバーがないため。GitHub 側に転送量の目安はあるが課金はされない） |
| CI | GitHub Actions | Public リポジトリは無料 |

### やらないこと（課金や情報漏えいにつながるもの）
- デモから **API を呼ばない**。不動産情報ライブラリ・e-Stat・LLM などの API は、学習時に手元で呼んで結果をファイルにしておき、デモには計算済みの結果とモデルだけを入れる
  - ブラウザ内で動く HTML に API キーを入れると、誰でも見られるため。また外部 API へのアクセスを中継する形になるのも避ける
- Cloud Run・BigQuery など **従量課金のサービスを公開 URL からアクセスできる状態にしない**（Module 09 で BigQuery を使うときも、デモからは直接つながない）
- API キーなどを Secrets に入れたワークフローを、外部からの PR で動かさない（`pull_request_target` は使わない）
- 定期実行（`schedule`）で外部 API や有料サービスを呼ぶワークフローは作らない（作る場合は手動実行 `workflow_dispatch` のみ）

### 入れておく保険
- GitHub の **Secret scanning / Push protection** を有効にする（API キーを誤ってコミットしかけたら止めてくれる）
- `.env` は `.gitignore` に入れ、`.env.example` には項目名だけを書く
- 不動産情報ライブラリの利用規約（出典の書き方・データを再配布してよい範囲）を確認し、README に出典を書く。生データはリポジトリに置かない
- Module 09 で GCP を使い始めるときは、最初に予算アラートを設定する
